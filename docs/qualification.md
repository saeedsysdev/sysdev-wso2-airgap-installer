# Implementation and qualification status

Milestone evidence updated 2026-11-01; no cluster, production registry, database, or identity service was contacted for qualification.

## Vendor documentation checked (2026-10-31)

- WSO2 API Manager 4.7.0's official compatibility documentation lists Temurin JDK 21/25 and Oracle 19c/23c as tested. The release notes state that JDK 21 or 25 is required. This supports the profile-level database/JDK candidates but does not qualify the proposed custom runtime image or Oracle integration code. [WSO2 product compatibility](https://apim.docs.wso2.com/en/latest/reference/product-compatibility/), [WSO2 4.7.0 release notes](https://apim.docs.wso2.com/en/latest/get-started/about-this-release/)
- Keycloak's official production configuration lists Oracle 19c 19.3+ as supported. Its Oracle database guide explicitly instructs container users to add `ojdbc17` and `orai18n` version `23.26.2.0.0` to a custom Keycloak image. That validates this candidate pair for Keycloak's documented Oracle setup only; it does not establish WSO2 compatibility or an end-to-end runtime pass. [Keycloak supported configurations](https://www.keycloak.org/server/supported-configurations), [Keycloak database guide](https://www.keycloak.org/server/db)
- No exact-version APIM Oracle JDBC-driver declaration, image build, Oracle connection, schema initialization, or failover test was executed. Keep those gates pending.

"Implemented" does not mean end-to-end product qualification. Tests use local fixtures, Kubernetes fake clients, and test HTTP/TLS services; no live cluster or production registry was contacted. `gofmt`, `go test ./...`, `go vet ./...`, and both release builds ran successfully with Go 1.27.3 on Windows. The Linux artifact is a cross-build. Native Linux tests and the race detector did not run locally because WSL had no Go toolchain and the attempted official download/package setup did not complete. CI is configured to run native Windows and Ubuntu tests and Linux race tests; those CI jobs have not run in this session.

The capacity assessment models all profile candidate replicas as unconstrained across the selected eligible workers because the pinned candidate profile defines no per-component node selectors/affinity. Existing nonterminal workloads with unknown placement constraints, taints/tolerations, or PVCs make recovery status unverified. The result remains a bounded CPU/memory preflight, not full scheduler simulation, HA certification, or a 400 TPS result. The single-control-plane and external-single-Oracle limitations are shown in review warnings.
